#### 31.20 THE SPREADER AND THE ROUTING CHAIN: built in a scratch copy, 2026-11-16 (lesson 1 follows; the repository has none of this code yet)

*Decisions of the user on 2026-11-16, after the measurement of 31.19. The code and its tests were built and checked in the scratch copy (the user types the product code, lesson by lesson). Nothing is committed and the registry order of `CHAIN` was not changed.*

| # | decision |
|---|---|
| **D112** | **THE RETRY RULE: 1 second, 3 seconds, then the next tier at once.** **(UPDATE 2026-11-23: the retry part is replaced by D129, section 33.6.)** A tier is called. If it does not answer, it is asked again after 1 s and once more after 3 s. Then the walk goes to the NEXT tier and wastes no time. This replaces the old rules (one or two retries with a growing wait, 3 s and 10 s for a 500, a wait for whatever `Retry-After` said, a 600 s read timeout). **What is retried:** no answer at all (a reset connection, an empty reply), 429 for a minute, 500, 502, 503, 504. **What is NOT retried:** 400, 401, 403, 404, 413, 422, a daily 429 (the pool is retired), a model that is not on the plan (429 with limit 0), a call refused locally (too long, missing key), an answer that cannot be read as JSON, an answer the caller rejects (the next tier writes it), and a hang that was cut off. **A provider that says "come back in 30 s" is not waited for:** a wait longer than 3 s means the next tier. The waits are in `RETRY_DELAYS` (`llm/defaults.py`) and a client can be built with `retry_delays=()` for a measurement of one model alone |
| **D113** | **A BUSY TIER IS SKIPPED, NEVER WAITED FOR (the spreader).** Before a tier is called the chain checks, in this order: its quota pool is not retired; the time budget is not spent; its minute ROOM has space (Google counts a room for each (key, model): 16,000 input tokens and 30 requests a minute for each Gemma model, so 6 rooms; Mistral 2 requests a minute for each model; Routeway 5, OrcaRouter 10, Token Harbor 60 for the account); its account is not already running the one call it allows (LiteRouter and Requesty: one at a time); and its account has rested long enough since the last call (LiteRouter: 8 s from the start of a call, and 1 s after one ends). A "no" on any of these is a skip with the reason written in the attempt, and the next tier is tried at once. The only wait left is a rest of at most `TURN_WAIT_MAX` = 2 s. The old second sweep that waited up to 30 s for the soonest room is gone. The place of a call is reserved under one lock, so two parallel calls never both see "free", and it is given back when the call ends, whether it answered or failed. **A call that failed still uses up its room** (measured on Google), which over-counts and is the safe direction |
| **D114** | **ONE ROUTE FOR EVERY TASK** (`labpilot/llm/routes.py`, the table below). A route is the list of tiers a task walks, by name, and the stop of a hung call. The routes were written from the quota, the limits, the speed (31.19) and the strength 1 to 5 of each tier. Rules that tests pin: every name is a live tier of `CHAIN`; no name twice; every route holds a Flash-Lite or Gemma 26B tier (those cannot run out); a tier that is not trusted is last; a task that sends MANY calls at the same moment starts with Google and has no one-at-a-time account among its first three tiers (the chain skips a busy LiteRouter for free, so it may stand later and serve a call that comes when it is free); Gemini 3.6 and 3.8 Flash (20 requests a day for each key) are only in the hard routes; Gemini 3.8 Flash (155 to 579 s for a call) is the last resort of the two-file answer only; every tier of a report route can write `REPORT_MAX_TOKENS`; every tier of a hard route has a window of 60,000 tokens or more and no per-minute input limit. `api/chains.py` has ONE function, `for_task(client, task)`, and it replaces `for_claims`, `for_trace`, `for_summary`, `for_skeptic`, `lead_with`, `only` and `bounded` |
| **D115** | **THE STOP OF A HUNG CALL (the one place that is not "no timeout").** The user asked for no timeout, so that no time is spent waiting on a dead tier. A call that never ends, however, would block its task for ever: one Token Harbor call stayed open for 40 minutes (31.19), because the server kept the connection alive and a read timeout, which counts the time between bytes, never fires. So each route carries a `stop`: 90 s for a small call, 240 s for a whole file in, 600 s for the answer the person reads. A call that has not answered by then is given up and the walk goes on, with no retry of that tier. Normal calls take 2 to 10 s and a report 150 to 400 s, so the stop only fires on a hang. The values are first guesses; `call_stop=None` on a client turns the stop off |
| **D116** | **(ENDED 2026-11-24 by D134: Token Harbor may be used.)** **THE TIERS THAT MAY BE READ BY THE PROVIDER ARE LEFT OUT BY DEFAULT.** Token Harbor's staff may read the chats of its free routes and the providers behind it may train on them (its own FAQ). The four Token Harbor tiers are in the routes but `resolve` leaves them out unless the caller passes `allow_readers=True`. The default is the safe one; the user has not yet decided whether to turn them on. The other free routes (Google's free tier, OpenRouter) were already accepted |
