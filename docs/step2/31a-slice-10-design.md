#### 31.1 What was wrong with the old plan, and why — the user's criticism, accepted

**The old plan.** Slice 10 had three new nodes: `extract_outcomes` (a table of every result a file reports, with what produced it, how it was measured and how it was chosen), "are these numbers comparable?" (YES, NO or CANNOT TELL for each pair) and "does it add up?". It came from the report template of Step 0 (sections 5, 6 and 9 there), and that template was shaped by one trap in the first test pair: the paper reports F1 0.851 on clean test data, the code reports 0.8262 on validation data whose threshold was tuned on itself, and an old model subtracted the two.

**The criticism (the user, 2026-11-12).** The node was designed from one pair and it does not generalize. The user's points, each checked:
1. **Results exist only in some inputs.** A paper has numbers. A notebook has cell outputs. A repository or a script has no results unless somebody runs it, and LabPilot's own code has none. Many cases are not machine learning at all. Even the quora file B has results only because someone copied the notebook outputs into a docstring by hand (see "The sample pair"). The pair that created the problem is the least typical one.
2. **Much of it already exists.** `prompts/answer.py` (`TWO_FILES`, lines 121 to 130) already asks for a COMPARABLE section (YES / NO / CANNOT TELL for each pair of numbers), for the causes with their sizes, and for the sum of the sizes against the gap. Claims already have a kind, `method` or `result` (`agent/claim.py`), so the result sentences of A are extracted at no extra cost. The instruction was measured in slice 6 (17.24): the "do the causes add up" verdict was right on 2 of 3 tiers. That is a SMALL sample (M18).
3. **Time.** The timer showed that `find_bugs` and `respond` are 79% of a run (29.24). More nodes mean more calls, for a problem that appears only when the question is about results.
4. **It is the exact mistake that 27.1 forbids.** A special case is not a solution. The rule was written on 2026-10-28 and it was broken again on 2026-11-10, when the slice 10 plan was written.

#### 31.2 What others do (web search, 2026-11-12)

*Search summaries only: the pages were NOT opened and read, so everything here is weaker than reading each paper.*

- **Tools that compare reported results with new results all RUN the code.** PaperRepro (arXiv 2603.00058) splits the job into running the scripts, capturing the new numbers, and then scoring with evidence. Kohler et al. ("Read Paper, Write Code") compare reproduced outputs with the original values in plain code and not with a model as the judge. AutoReproduce (2505.20662) re-runs the experiments and uses the new results as the ground truth. PaperBench (2504.01848) has "result match" checks that compare numbers made by a reproduction run with the paper's numbers, within a tolerance. LabPilot only READS files, so these systems solve a different problem.
- **Nothing was found about metrics that are not comparable, for a tool that only reads.** The search itself suggested other search words ("evaluation protocol mismatch", "reported vs reproduced metric discrepancy"); they were not tried.
- **Asking the user when evidence is missing is a common practice, not a standard.** Spring AI has an ask-the-user tool that pauses the task; a DEV article and the STYLE paper (2405.12059) describe the same idea: when retrieval finds nothing for a needed fact, ask instead of guessing. Advice repeated by the sources: ask at most one question, make it specific, give options when possible, ask only when a wrong guess is costly, and use a structure and not a prompt rule to limit the number of questions. These are blogs and write-ups.

**D109 in detail.**

- **What it is.** The planner answer gets a new field, `ask`: empty (most messages) or ONE short question. When it is not empty, the graph pauses right before `respond` (after the last merge). The page shows the question. The user answers or skips. The answer goes into its own block of the one answer-prompt function (a new state key with the replace rule, cleared by `remember` like `summary_a`, so that an old answer never leaks into the next message). Then `respond` writes the report. The idea and the place (at the END of the agent process) are the user's. It has one good side: the files have been read, so a question could be exact.
- **The planner decides, at the start.** It has not read any findings yet, so the first version lets the planner write the question itself. A better question written at the end, when the findings are known, costs one more model call; add it only if the questions are poor.
- **It is general, not only for results.** Examples: results ("What F1 did you get, and on which data?"); something only the user knows ("Which split did you tune the threshold on?"); an unclear follow-up ("You said 'fix the bug'. Which of the 5 bugs?"). It works on a first message and on a follow-up.
- **Rules.** At most one question; short; options when possible; skip is always possible and a skipped question still gives a normal answer. Ask only when a wrong guess costs a lot, and the first example is a person who talks about THEIR OWN result without saying what it is or how it was measured ("My numbers came out lower. Why?"), because the planner decides at the start and sees the person's words, not the numbers printed by the files. **When the planner is unsure it does NOT ask** (the opposite of the other D107 choices, because a missing question only makes the answer a little less exact, while a wrong pause wastes the user's time). On a follow-up (the fast path) ask only when the answer would really be a guess. **The field is checked in code, changed 2026-11-13:** only a question that REPEATS the person's own makes the plan a problem (the next tier writes it again, D50). Line breaks are NOT a problem: they become spaces and the question is kept. A question longer than `MAX_ASK_CHARS = 400` is dropped by the last guard and the steps and queries stay, because the text goes to the page and into the next prompt, and the planner reads parts of the files in its map. A bad or repeated question that is left at the last guard is dropped and the plan is kept.
- **B (slice 10).** LangGraph's `interrupt` and `Command(resume=...)`, with the Postgres saver. The first request can now return "a question" instead of a report, so the `/compare` reply, the request (the answer, or skip), the page contract and the throwaway page all change: this is a medium job and not a small toy. **There is no timer in B.** The run is parked: no process runs while it waits (and Render's free server sleeps when idle). It waits until the user answers, presses skip, or sends a new message, which counts as skip.
- **C (Step 3).** The server runs the message in the background. The page shows the question while `find_bugs` and the other slow steps run (the user's idea: use the waiting time). The answer is attached before `respond` starts, and `respond` then streams the report. Claude and ChatGPT usually ask first and wait, so "ask while it works" is something we add on top. **If the user does not answer in 1 minute, the question counts as skipped and the run goes on. The 1 minute is the user's decision. It is NOT a guess and it is NOT in the tuning list of 27.2.** A browser notification tells the user to answer: the Notifications API while the tab is open (with the user's permission), a changed tab title and a sound; a notification when the tab or the browser is closed needs a service worker and a server push, which is more work. C needs the background run, a channel to the page (SSE) and a second route for the answer. It is the same job that the notes for Step 3 already list (progress display and SSE). **In Step 3 we try C; if it is worth it we keep it, and if not we do what Claude and other agents do.** The beautiful UI component (not a plain text box) is also a Step 3 job; for now it is only designed. **Measured 2026-11-12 (31.9, point 8): `interrupt` cannot do C. A pause is shown to the caller only when the whole step ends, so a question in the same step as `find_bugs` arrives after `find_bugs`; a separate node does not change it. C needs a background run and a table for the answer, not `interrupt`.**
- **Risks of B: TESTED on 2026-11-12 (31.9). Before the test they were (all from memory):** `interrupt` starts the paused node again from its first line when it resumes; how it works with the save-once rule (`durability="exit"`, D36) and with `PRUNE`; whether the other nodes of the same step finish while one node is paused. A toy file, `examples/langgraph/graph_with_interrupt.py`, typed by the user as a lesson, answers these before anything is built.

#### 31.9 The `interrupt` probe and the scratch build of the pause (D109, B)

**Probe on the real Postgres saver (throwaway schema), all measured on 2026-11-12:**
1. `invoke` returns normally; its result holds `__interrupt__`, a list of `Interrupt(value=..., id=...)`.
2. On resume the paused node starts again from its FIRST line; a parallel node of the same step is not run again.
3. `durability="exit"` saves the pause: a new connection and a new graph object resume it (the second HTTP request).
4. Our `PRUNE` after the pause breaks nothing, before or after the resume.
5. A NEW message on a parked chat does not cancel the pause: it starts the graph again from the beginning (the slow node ran twice) and may pause again.
6. `Command(resume=None)` CRASHES LangGraph 1.2.12 (`UnboundLocalError: resume_is_map`, `_loop.py` line 927). A skip is the empty text.
7. A reply to a chat that is NOT paused does nothing and returns the OLD result with no error (in-memory saver; on an unknown chat it raises `KeyError: 'question'`). So `ask()` checks `get_state(config).next` before it resumes and raises `NothingToAnswer` (409, `nothing_to_answer`) when nothing is waiting. The check catches a late duplicate (an old tab, a retry after the run finished). A double click is already stopped by the page, which hides the box at once; two replies in flight at the same time are NOT stopped by this check. The user chose that the real page ignores this one error quietly and keeps the report on screen.
8. **A pause in the same step as a slow node does not show the question early** (toy: a slow node of 4 s beside a node that only calls `interrupt`). The question reached the caller at 4.0 s, when the step ended, with `invoke` and with `stream`. A separate node does not help: the tested ask node WAS a separate node. An answer sent at 1 s from a second thread was accepted (the asker got it at 1.0 s), but the slow node then ran twice (it finished at 4.0 s and again at 5.0 s) and the first call still returned "waiting". Two calls on one chat at the same time are not safe, so this is not a way to build C. The ask node can be placed (a) beside the slow nodes (no gain), (b) in a step before them (the question comes early, nothing runs while the person answers; reasoned, not run) or (c) right before `respond` (B, the plan).
